# 5 Отладка и тестирование веб-приложения «ЭкваЛайн»

В данной главе описан процесс ревьюирования значимых фрагментов программного кода серверной части и клиента, ручное тестирование пользовательских сценариев и варианты публикации приложения в сети Интернет.

## 5.1 Ревьюирование программного кода

Ниже приведены **восемь** типовых результатов ревью: для каждого — фрагмент **до** улучшения (антипаттерн или устаревший вариант) и фрагмент **после** (текущее или целевое состояние в проекте «ЭкваЛайн»). Нумерация **Пример 1…8** удобна для перекрёстных ссылок и списка иллюстраций в редакторе отчёта (Word нумерует заголовки или отдельный список автоматически при вставке).

### Пример 1. Валидация телефона (Joi, единый формат в базе)

**До рефакторинга** — только литеральный шаблон `7` + 10 цифр; ввод «с восьмёрки» отклоняется без объяснения для пользователя админ-панели.

```javascript
phone: Joi.string().pattern(/^7\d{10}$/).required(),
```

**После рефакторинга** — нормализация цифр и та же финальная проверка; сообщение Joi на русском.

```javascript
function normalizeRuPhoneForSchema(raw) {
  let d = String(raw ?? '').replace(/\D/g, '');
  if (d.length === 11 && d[0] === '8') return `7${d.slice(1)}`;
  if (d.length === 10 && d[0] === '9') return `7${d}`;
  return d;
}

const ruPhoneSchema = Joi.string().custom((value, helpers) => {
  const n = normalizeRuPhoneForSchema(String(value ?? '').trim());
  if (!/^7\d{10}$/.test(n)) {
    return helpers.message({
      custom: 'Телефон: 11 цифр номера России (можно указать через 7 или через 8).',
    });
  }
  return n;
});
```

*Файл:* `schemas.js`.

### Пример 2. Запрос к СУБД (защита от SQL-инъекций)

**До рефакторинга** — динамическая подстановка значения пользователя в текст SQL (учебный **антипаттерн**; допускает инъекцию через `req.body.phone`).

```javascript
const phone = req.body.phone;
const row = db.prepare(`SELECT id FROM users WHERE phone = '${phone}'`).get();
```

**После рефакторинга** — подготовленное выражение, параметры передаются отдельно от текста запроса.

```javascript
const exists = await db
  .prepare('SELECT id FROM users WHERE lower(email) = lower(?) OR phone = ?')
  .get(email, phone);
```

*Файл:* `server.js` (обработчик создания пользователя администратором; аналогично — регистрация, обновление профиля).

### Пример 3. Сессия после входа и регистрации (PostgreSQL-хранилище)

**До рефакторинга** — присвоение `req.session.userId` и немедленный ответ без гарантии записи сессии на диск/в БД; при использовании `connect-pg-simple` клиент мог получить редирект раньше, чем сессия сохранится.

```javascript
req.session.userId = user.id;
res.json({ user: publicUser(user) });
```

**После рефакторинга** — явное ожидание сохранения сессии.

```javascript
async function saveSessionPromise(req) {
  return new Promise((resolve, reject) => {
    if (!req.session) return resolve();
    req.session.save((err) => (err ? reject(err) : resolve()));
  });
}
await saveSessionPromise(req);
res.json({ user: publicUser(user) });
```

*Файл:* `server.js`.

### Пример 4. Геокодирование с клиента (централизация и ключ API)

**До рефакторинга** — прямой вызов публичного Nominatim из браузера; ключ Яндекса на картах не скрыт за бэкендом, политика лимитов внешнего сервиса на стороне клиента.

```javascript
const url = `https://nominatim.openstreetmap.org/search?${params.toString()}`;
return fetch(url, { headers: { Accept: 'application/json' } }).then((r) => r.json());
```

**После рефакторинга** — запрос к собственному API приложения; на сервере выбор Яндекс/Nominatim и единая нормализация ответа.

```javascript
const url = `/api/public/geocode-search?${params.toString()}`;
return fetch(url, {
  credentials: 'same-origin',
  headers: { Accept: 'application/json' },
})
  .then((response) => {
    if (!response.ok) throw new Error('geocode_failed');
    return response.json();
  })
  .then((rows) => (Array.isArray(rows) ? rows : []));
```

*Файл:* `script.js` (функция `geocodeAddress`); серверная реализация — `geocode-proxy.js`, подключение в `server.js`.

### Пример 5. Изменяющие запросы к API и CSRF

**До рефакторинга** — произвольный `fetch` без токена при `POST`/`PATCH` (при включённой проверке на сервере запрос получит `403`).

```javascript
fetch('/api/profile', {
  method: 'PATCH',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(data),
});
```

**После рефакторинга** — получение токена с `/api/csrf` и заголовок `X-CSRF-Token` для небезопасных методов (обёртка `apiFetch`).

```javascript
async function apiFetch(path, options = {}) {
  const headers = { ...(options.headers || {}) };
  const method = (options.method || 'GET').toUpperCase();
  if (method !== 'GET' && method !== 'HEAD') {
    let t = await ensureCsrf(false);
    if (!t) t = await ensureCsrf(true);
    if (t) headers['X-CSRF-Token'] = t;
  }
  if (options.body && typeof options.body === 'object' && !(options.body instanceof FormData)) {
    headers['Content-Type'] = 'application/json';
    options.body = JSON.stringify(options.body);
  }
  const r = await fetch(path, {
    ...options,
    credentials: 'same-origin',
    headers,
  });
  return r;
}
```

*Файл:* `api-client.js`; на сервере маршруты защищены `csrfMiddleware` в `server.js`.

### Пример 6. Политика сложности пароля при регистрации и в админке

**До рефакторинга** — минимальная длина без проверки состава символов (слабые пароли проходят валидацию).

```javascript
password: Joi.string().min(8).max(128).required(),
```

**После рефакторинга** — общая схема `passwordSchema`: заглавная и строчная буква, цифра, спецсимвол.

```javascript
const passwordSchema = Joi.string()
  .min(8)
  .max(128)
  .pattern(/[A-ZА-ЯЁ]/)
  .pattern(/[a-zа-яё]/)
  .pattern(/\d/)
  .pattern(/[!@#$%^&*()_+\-=[\]{};':"\\|,.<>/?]/)
  .messages({
    'string.min': 'Пароль: минимум 8 символов.',
    'string.max': 'Пароль: не более 128 символов.',
    'string.pattern.base':
      'Пароль: нужны заглавная и строчная буквы, цифра и спецсимвол (!@#$…).',
  });
```

*Файл:* `schemas.js` (используется в `registerSchema`, `adminUserCreateSchema` и т.д.).

### Пример 7. Подключение карты на странице «Доставка» (единый загрузчик)

**До рефакторинга** — в HTML явно подключены CSS/JS Leaflet и инициализация только при наличии глобального `L`; без единого выбора провайдера (Яндекс или OSM).

```html

<script src="https://unpkg.com/leaflet@1.9.4/dist/leaflet.js"></script>
```

```javascript
const map = L.map(deliveryLeafletMap).setView([51.768, 55.102], 12);
L.tileLayer('https://{s}.tile.openstreetmap.org/{z}/{x}/{y}.png', { maxZoom: 19 }).addTo(map);
```

**После рефакторинга** — общий скрипт `maps-runtime.js`, конфигурация `/api/public/maps-config`, при наличии ключа Яндекс-карт подгружается их API, иначе подключается Leaflet из кода; на странице доставки вызывается `EkvalineMaps.initStaticMap`.

```html
<script src="maps-runtime.js"></script>
```

```javascript
if (deliveryLeafletMap && window.EkvalineMaps && typeof window.EkvalineMaps.initStaticMap === 'function') {

```

*Файлы:* `delivery.html`, `maps-runtime.js`, `script.js`.

### Пример 8. Хранение и проверка пароля (не хранить открытый текст)

**До рефакторинга** — пароль пользователя записывается в таблицу **как есть** и при входе сравнивается строкой; при компрометации БД пароли читаются напрямую (учебный **антипаттерн**).

```javascript
await db
  .prepare('INSERT INTO users (email, password, first_name) VALUES (?, ?, ?)')
  .run(email, password, firstName);

const row = await db.prepare('SELECT * FROM users WHERE email = ? AND password = ?').get(email, password);
if (!row) return res.status(401).json({ error: 'Неверный логин или пароль.' });
```

**После рефакторинга** — перед записью вычисляется **криптографический хэш** (`bcrypt`), в БД сохраняется только `password_hash`; при входе используется **`bcrypt.compareSync`**, исходный пароль в хранилище не фигурирует.

```javascript
const password_hash = bcrypt.hashSync(password, 12);
const info = await db
  .prepare(
    `INSERT INTO users (email, phone, password_hash, first_name, last_name, role, password_changed_at)
     VALUES (?, ?, ?, ?, ?, 'client', datetime('now'))`
  )
  .run(email, phone, password_hash, first_name, last_name || '');
if (!bcrypt.compareSync(password, user.password_hash)) {
  await recordLoginFail(user.id);
  return res.status(401).json({ error: 'Неверный логин или пароль.' });
}
```

*Файл:* `server.js` (маршруты **регистрации** и **входа**, аналогичная схема — при создании пользователя из админ-панели через `bcrypt.hashSync`).

## 5.2 Тестирование веб-приложения

Для тестирования веб-приложения «ЭкваЛайн» выбран метод **ручного тестирования** по контрольным сценариям на собранном локально или развёрнутом стенде (`npm start`, доступ по `http://localhost:3001` или к домену заказчика).

### Наличие обязательных полей и реакция интерфейса

В приложении реализованы формы, где пустые обязательные поля не должны проходить без сообщения пользователю:

| Зона | Где в проекте | Обязательность |
|------|----------------|----------------|
| **Авторизация** | Модальное окно в `script.js` — поля логина (email или телефон) и пароля | При пустых полях выводится сообщение «Заполните логин и пароль» (логика в обработчике отправки формы). |
| **Регистрация** | Та же модалка: имя, email, телефон, пароль | Проверка на клиенте и на сервере по `registerSchema` (`schemas.js`). |
| **Профиль в кабинете** | `cabinet.html` / `cabinet-pg.js` | Обязательные поля профиля и телефон в формате 11 цифр после нормализации. |
| **Обратная связь** | `contacts.html` | Имя, телефон, текст сообщения (не менее 10 символов по схеме `feedbackSchema`). |
| **Создание пользователя админом** | `admin.html` / `admin.js`, API `POST /api/admin/users` | Поля ФИО, email, телефон, пароль, роль; для роли «Водитель» — метка маршрута. |
| **Оформление заказа** | Корзина / чекаут в `script.js` | Выбор слота, адрес, контактные данные — в зависимости от сценария (карта/текст). |

Учётные данные для проверки входа сотрудников и демо-клиента приведены в **`docs/DEMO_PASSWORDS.md`** (не публиковать в открытом отчёте без замены на обезличенные примеры при необходимости).

### Порядок контрольного примера (авторизация / регистрация)

1. Открыть главную страницу сайта, нажать **«Вход»**.
2. Нажать кнопку отправки формы **не заполняя** поля — убедиться, что появляется сообщение о необходимости заполнения.
3. Ввести **некорректный** телефон или слабый пароль при регистрации — убедиться, что сервер/клиент возвращают понятную ошибку (схемы Joi и подсказки в форме).
4. Выполнить **успешный** вход под демо-ролью (например, оператор) и убедиться в переходе на `operator.html` или сохранении сессии согласно роли.

## 5.3 Публикация веб-приложения в сети

Развёртывание веб-приложения «ЭкваЛайн» может выполняться **передачей исходного кода заказчику** в виде **структурированного архива ZIP** либо через **репозиторий Git** на платформе **GitHub** или **GitLab**. Использование системы контроля версий позволяет отслеживать изменения, вести ветки релизов и организовать совместную разработку.

**Серверная часть** реализована на **Node.js** (рекомендуется среда выполнения **версии 18 и выше**). Для полного функционала (сессии, заказы, админ-панель на API) используется **PostgreSQL** (целесообразно **версии 14 и выше**). На рабочих стендах трафик должен идти по протоколу **HTTPS**; для этого настраивается **доменное имя**, получается и устанавливается **SSL/TLS-сертификат**.

Типовые варианты размещения:

- **VPS / облако** (Linux или **Windows Server 2019 и выше**): установка **Node.js**, **PostgreSQL**, клонирование репозитория, настройка переменных окружения (в т.ч. `SESSION_SECRET`, `PGPASSWORD`, при использовании карт — `YANDEX_MAPS_API_KEY`), выполнение миграций/скриптов БД по документации проекта.
- **Публикация за обратным прокси**: **IIS** с модулем **Application Request Routing (ARR)** или **nginx** / **Caddy** на Linux — проксирование запросов на процесс `node server.js` (порт приложения задаётся переменной **`PORT`**, по умолчанию в проекте **3001**).
- Альтернатива для небольших стендов — прямой доступ к порту Node за файрволом (только для тестов); для продакшена обязателен HTTPS и прокси.

**Статические страницы** (`index.html`, `admin.html`, `operator.html`, `cabinet.html` и др.) отдаются через **`express.static`** из каталога приложения. В отчёте для пользователей целесообразно указать **основной URL** сайта, например `https://ekvaline.ru`. Панель администратора открывается отдельной страницей **`admin.html`**, то есть типичный адрес вида **`https://ekvaline.ru/admin.html`** (не смешивать с REST-маршрутами вида `/api/admin/...`, которые вызываются скриптами после входа).

**Проверка после размещения** (чек-лист):

- открытие главной страницы в браузерах **Chrome**, **Firefox**, **Safari**, **Edge**;
- при наличии HTTPS — редирект с **HTTP** на **HTTPS**;
- регистрация и авторизация **валидными** и **невалидными** данными;
- оформление **тестового заказа** (разные сценарии адреса и времени доставки);
- **личный кабинет клиента** — просмотр заказов и обновление профиля;
- **панель администратора** — добавление/редактирование товаров, работа с пользователями и заказами (по роли);
- **калькулятор потребления воды** на главной;
- форма **обратной связи** на странице контактов;
- резервное копирование **PostgreSQL** по регламенту заказчика (расписание, каталог хранения копий — на стороне инфраструктуры; в коде проекта задаётся политика окружения).

Доступ к размещённому приложению: для клиентов — по основному домену; для администратора — страница **`admin.html`** и учётная запись суперпользователя (логин, пароль и краткая инструкция передаются заказчику отдельным защищённым каналом, пароли после первого входа рекомендуется сменить).

## 6.2 Техническое сопровождение (материал для следующей главы отчёта)

*При оформлении отчёта этот блок можно вынести в главу 6; ниже текст адаптирован под стек «ЭкваЛайн».*

В процессе эксплуатации веб-приложения «ЭкваЛайн» необходимо регулярно выполнять действия по поддержанию работоспособности: **резервное копирование базы PostgreSQL** по согласованному регламенту (например, ежедневно с сохранением копий на удалённом сервере или в облаке — **Yandex Cloud**, **Selectel** и т.п.), **проверка логов** приложения Node.js и системного журнала сервера на предмет ошибок и попыток несанкционированного доступа, **обновление зависимостей** через **`npm`** после тестирования на копии стенда, установка обновлений безопасности для **ОС** и среды **Node.js**.

Разделение ответственности: изменение **контента** (каталог, цены, зоны доставки, публикации блога) по возможности выполняется заказчиком через **панель администратора** (`admin.html`) без правки исходного кода; изменения **программного кода** — разработчиком.

При сбоях рекомендуется иметь регламент восстановления: остановка процесса приложения, восстановление БД из резервной копии средствами **`pg_restore`** / **`pg_dump`**, перезапуск службы Node, проверка API и ключевых страниц.

Техническая поддержка может включать консультации по эксплуатации, мониторинг загрузки CPU/RAM/диска, настройку масштабирования при росте нагрузки. Для веб-производительности периодически имеет смысл использовать **Google PageSpeed Insights** и **Яндекс Вебмастер** / аналоги для оценки скорости загрузки. Автоматизация регламентных скриптов на **Windows Server** возможна через **Планировщик заданий** и **PowerShell**; на **Linux** — через **cron** и shell-скрипты. Конфигурационные файлы (`.env`) хранить с ограниченными правами доступа.
