# Программа ревьюирования кода «ЭкваЛайн»

Документ описывает **повторяемый** процесс анализа кода до выкладки в промышленную эксплуатацию: не разовую проверку, а регламент с фиксацией результатов.

**Примеры кода «до / после»** — отдельный файл **[ПРИМЕР-РЕВЬЮ-ДО-ПОСЛЕ.md](./ПРИМЕР-РЕВЬЮ-ДО-ПОСЛЕ.md)** (только фрагменты кода).  
Дублирование с комментариями — ниже в [примере ревью](#пример-ревью-образец-заполнения), блоки **DEF-01** и **DEF-02** → `#### Пример кода: до / после`.

## Цели

- Раннее обнаружение логических ошибок (рассогласование UI и API, статусы заказов, синхронизация клиент ↔ сервер, права ролей).
- Контроль архитектуры: без дублирования критичной логики, без единственного источника истины в браузере, без обхода ограничений без проверки на сервере.
- Аудит критических зон: сессии и вход, CSRF, БД, бонусы и суммы заказов, массовые смены статусов, конфигурация среды.

## Классы дефектов (что искать)

1. **Согласованность UI ↔ сервер** — валидация только на одной стороне; разные названия статусов в `operator.js` и `server.js`.
2. **Граничные значения** — пустые строки, NaN, даты без учёта локали, сравнение чисел из строк с пробелами.
3. **Идемпотентность** — двойной клик «Сохранить», параллельные PATCH без транзакции.
4. **localStorage** — отображение прав только из LS без `GET /api/auth/me` (панели staff/client).
5. **Архитектура** — монолитные файлы, циклические зависимости, цены/бонусы только в `script.js`.
6. **Безопасность** — сессия, CSRF, SQL-инъекции, хэши паролей, утечка ключей карт/геокодера, stack trace в production.

## Контрольный чеклист (полный цикл)

- [ ] `npm run verify` — успешно
- [ ] Сервер поднимается с БД (`npm start` / Docker), дымовой вход: client, operator, admin
- [ ] Новые/изменённые маршруты проходят `schemas.js` (Joi)
- [ ] Изменения заказов пишутся в `audit_log` / `order_audit_events`
- [ ] В production нет детальных stack trace клиенту (`NODE_ENV=production`)
- [ ] Связанные сущности (заказ + бонусы + остаток) — в транзакции (`db.withTransaction`)
- [ ] Запросы к PostgreSQL параметризованы (без конкатенации SQL)
- [ ] CSRF на мутациях; клиент обрабатывает 401 / `sessionExpired`
- [ ] Нет боевых секретов в репозитории (только `.env.example`)
- [ ] `npm audit` задокументирован (обновление или принятие риска)

## Отчётность

По итогам квартала или крупного релиза — краткий отчёт: дата, ветка/тег, `npm audit`, список дефектов (приоритет + задача), архитектурные замечания, **вывод**: допуск / не допуск к деплою.

Программа **не заменяет** нагрузочное тестирование и полноценный UX-тест.

## Найденные дефекты и статус

### DEF-01 — Рассогласование формата `items_json` (клиент ↔ оператор)

| | |
|--|--|
| **Приоритет** | Высокий (влияет на отчёты и работу оператора) |
| **Статус** | **Исправлено** в рамках ревью |
| **Где** | `server.js` (`POST /api/orders`), `operator.js` (`parseQty`, `footerBottleQtyFromOrder`) |

**Описание.** Клиентский заказ сохранял состав как объект `{ lines: [...], subtotal, ... }`, а панель оператора ожидала массив `[{ title, qty, unit_price }]`. В таблице отображалось **Кол-во: 0** и **0 бутылей** при корректной `total_sum`.

**Рекомендация (выполнена).**

- Сервер: `items_json = JSON.stringify(lineItems)` с полями `title`, `qty`, `unit_price`, `product_id`.
- Оператор: единая функция `extractOrderItemsArray()` для старого и нового формата.
- Миграция: `migrateClientOrderItemsJson()` в `db.js` для существующих строк.

**Проверка после исправления.** Создать заказ с каталога → в `operator.html` колонки «Кол-во» и итог по бутылям совпадают с корзиной.

### DEF-02 — Сессия не завершалась при бездействии пользователя

| | |
|--|--|
| **Приоритет** | Средний (безопасность) |
| **Статус** | **Исправлено** |
| **Где** | `server.js`, `api-client.js`, `script.js`, `cabinet-pg.js`, `operator.js` |

**Описание.** Cookie с `rolling: true` и фоновый опрос заказов в кабинете продлевали сессию без действий пользователя. Требование: редирект на вход после длительного простоя.

**Рекомендация (выполнена).**

- `SESSION_IDLE_MINUTES` (по умолчанию 30), `lastActivityAt` в сессии.
- Продление только при `X-User-Activity: 1` (клиент) или мутациях API.
- Ответ `401` + `sessionExpired: true`; клиент → `index.html?session-expired=1` и модальное окно входа.

**Проверка.** Войти → не трогать страницу > 30 мин (или уменьшить `SESSION_IDLE_MINUTES=2` в `.env` для теста) → любой защищённый запрос должен разлогинить.

### POS-01 — Положительные результаты (зафиксировать)

- Цены состава заказа пересчитываются на сервере (`order-pricing.js`), клиент не может занизить сумму через DevTools.
- CSRF на мутациях; `requireAuth` + `requireRole` на staff-маршрутах.
- Пароли: `bcrypt`; панель оператора сверяет сессию через `hydrateStaffFromServerSession()` + `staffSessionOk`.
- Параметризованные запросы в `db.js` (плейсхолдеры `?` / `$1`).
- `security-middleware.js`: заголовки, rate limit, проверка `SESSION_SECRET` в production.
