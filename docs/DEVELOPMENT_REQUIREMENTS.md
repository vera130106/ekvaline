# 2.2 Требования к разработке (для проекта «ЭкваЛайн»)

Документ фиксирует требования и фактические решения по разработке веб-приложения в текущем проекте `dpp`.

---

## 2.2.1 Среда разработки

Разработка проекта выполняется в IDE с поддержкой HTML/CSS/JavaScript и Node.js.

### Рекомендуемая среда

- `Cursor` / `VS Code` (фактически используется в проекте);
- допускается использование `Sublime Text` или `Notepad++` для отдельных задач;
- для ускорения верстки можно использовать `Emmet`.

### Базовые требования к рабочему месту

- ОС: Windows 10+;
- `Node.js` и `npm` установлены;
- доступ к локальному PostgreSQL;
- доступ к `Git`-репозиторию проекта.

---

## 2.2.2 Технологии

В проекте используется клиент-серверная архитектура с API и разграничением ролей.

### Серверная часть

- платформа: `Node.js`;
- веб-сервер приложения: `Express` (`server.js`);
- валидация данных: `Joi` (`schemas.js`);
- сессии и безопасность: `express-session`, `cookie-parser`, `csrf`;
- хеширование паролей: `bcrypt`;
- хранение данных: `PostgreSQL` (прямой доступ через `pg` и `db.js`).

### Клиентская часть

- языки: `HTML`, `CSS`, `JavaScript`;
- клиент API: `api-client.js`;
- основные сценарии: `script.js`, `operator.js`, `cabinet-pg.js`, `manager.js`, `community.js`.

### Развёртывание

- локально: запуск через `npm start`;
- в production рекомендуется reverse proxy через `Nginx` (проксирование на Node.js);
- все клиентские страницы отдаются как статика, бизнес-операции идут через `/api/*`.

---

## 2.2.3 Требования к интерфейсу

### Общие требования

- интерфейс на русском языке;
- соблюдение корпоративного стиля (цвета, типографика, единые состояния кнопок/полей);
- адаптивность для desktop и laptop;
- единообразие поведения форм (валидация, сообщения об ошибках, успешные уведомления).

### Графические элементы

- макеты могут подготавливаться в `Figma` / `Adobe Illustrator`;
- допустимые источники графики: `Flaticon`, `Wepik`, `Storyset` (с проверкой лицензий);
- иконки/изображения должны быть оптимизированы для web.

### Функциональные элементы интерфейса

- форма обратной связи;
- регистрация, вход, выход;
- личный кабинет клиента;
- оформление и редактирование заказа;
- операторская панель и административные разделы.

Все перечисленные действия должны работать через API и сохраняться в базу данных.

---

## 2.2.4 Требования к разработке базы данных

### СУБД

- основная СУБД проекта: `PostgreSQL` (актуальная реализация);
- язык запросов: `SQL`.

### Требования к структуре

- база должна соответствовать информационной модели приложения;
- ключевые таблицы: `users`, `orders`, `products`, `categories`, `feedback_messages`, `audit_log`, `delivery_addresses`, `delivery_zones`, `site_settings`, `bonus_operations`;
- связи и ограничения должны обеспечивать целостность данных (PK/FK, обязательные поля, уникальность email/phone).

### Требования к безопасности БД

- доступ к БД только через серверное API;
- учетные данные БД хранятся в `.env`, не коммитятся в репозиторий;
- пароли пользователей в БД хранятся только в виде хешей (`bcrypt`);
- права доступа к данным должны ограничиваться ролью пользователя;
- изменения важных сущностей логируются в `audit_log`.

---

## 2.2.5 Требования к разграничению прав

В приложении реализуются роли:

- `client` — личный кабинет, свои заказы;
- `operator` — обработка и изменение заказов;
- `manager` — управление публичными настройками/контентом по доступным разделам;
- `admin` — управление пользователями, адресами, зонами доставки и административными функциями.

### Обязательные требования

- обязательная авторизация для защищённых разделов;
- проверка прав доступа на сервере для каждого API-эндпоинта;
- запрет доступа к чужим данным для клиентов;
- хранение факта ключевых действий пользователей в журнале (`audit_log`).

---

# 2.3 Тестирование и документация

Для подтверждения корректности работы веб-приложения требуется:

## 2.3.1 Тестирование

- функциональное тестирование всех пользовательских сценариев:
  - форма обратной связи,
  - регистрация/вход,
  - оформление заказа,
  - действия оператора и администратора;
- интеграционное тестирование API и БД (корректность CRUD-операций, ролевая модель);
- проверка валидации и негативных сценариев (ошибочные/неполные данные);
- регрессионная проверка после изменений в серверной логике.

## 2.3.2 Документация

Необходимо поддерживать в актуальном состоянии:

- описание архитектуры проекта;
- описание структуры БД и ролей пользователей;
- инструкцию по локальному запуску и развертыванию;
- перечень API-эндпоинтов и форматов данных;
- описание процедур резервного копирования и восстановления БД (для production).

## 2.3.3 Контроль версий

- использование `Git` обязательно;
- изменения вносить атомарно и осмысленно;
- перед релизом выполнять проверку работоспособности основных сценариев.
